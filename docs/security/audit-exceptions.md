# Dependency audit exceptions

`pnpm audit --audit-level=high` blocks CI (`.github/workflows/ci.yml`, job "Dependency audit"). An advisory may
be ignored only when **no fix exists** and the vulnerable code is not reachable by untrusted input. Every entry
needs a justification, an owner, an expiry date (≤ 30 days, renewable after review) and a `security-engineer`
review (CLAUDE.md §7). Entries live in `pnpm-workspace.yaml` → `auditConfig.ignoreGhsas`; remove them as soon as a
patched version is published (then upgrade or override). Expired entries are a CI-hygiene defect.

`ignoreGhsas` is per advisory, not per path: an exception is void the moment the package appears in a production
path (`pnpm why <pkg> --prod` in any workspace must stay empty) and must be re-reviewed whenever the lockfile adds a
new path to it. This rule applies to every exception except the one narrow class below.

**Class T — toolchain package in the prod dependency graph, proven absent from shipped artefacts** (product owner,
2026-10-03; `security-engineer` review 2026-10-03). Some runtime dependencies carry their build CLI with them (for
example `expo` depends on `@expo/cli`), so a tool that only runs on developer and CI machines shows up under
`pnpm why --prod`. Such an advisory may be excepted only when all of these hold:

1. every `pnpm why <pkg> -r --prod` path goes through the named toolchain package (the entry lists them); any other
   path voids the exception;
2. the package is listed in `apps/mobile/bundle-forbidden-packages.json`, and the `bundle:check` CI step proves on
   every affected PR that it is not a module in the `expo export` source maps for android or ios (the check fails
   closed on a missing map). A drift test keeps that file, this register and `ignoreGhsas` in step;
3. it is in no service image or other shipped artefact, and the vulnerable code is not reachable by untrusted input
   in the configuration we use (written analysis in the entry);
4. no fix exists, and the entry has an owner, an expiry ≤ 30 days and explicit invalidation rules. When a fix is published, `minimumReleaseAge` (3 days) delays adoption; do not bypass it — schedule
   the upgrade for the day it becomes installable.
